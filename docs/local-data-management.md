# 로컬 데이터 관리 운영 가이드

이 기능은 대학알리미 학과별 재적학생 XLSX를 업로드하고, 검증된 버전만 일반 대시보드에 게시하는 2단계 로컬 MVP입니다.

> 현재 데이터 관리 기능은 로컬 MVP 전용입니다. 인터넷에 배포하기 전에 관리자 로그인과 서버 저장소를 반드시 연결해야 합니다.

## 1. 최초 데이터 이관

기존 2023~2025 원본은 이동하거나 수정하지 않습니다. 다음 명령은 원본 바이트를 읽어 비공개 저장소에 복사하고, 각 연도를 최초 게시 버전으로 등록합니다.

```powershell
pnpm data:migrate -- --input-dir "C:\Users\user\Downloads\data_20260731153427"
pnpm data:store:validate
```

이관 기준은 2023년 14,480행, 2024년 15,056행, 2025년 15,706행, 총 45,242행, 2025년 재적학생 2,128,443명입니다. 명령은 SHA-256 중복을 인식하므로 다시 실행해도 같은 파일을 새 버전으로 만들지 않습니다.

## 2. 관리자 화면 사용법

1. `pnpm dev`로 서버를 실행합니다.
2. `http://127.0.0.1:3000`을 열고 왼쪽 `데이터 관리`로 이동합니다.
3. 현재 게시 현황에서 활성 연도·버전·행 수·게시 시각·검산 상태를 확인합니다.
4. XLSX 한 개를 놓거나 선택하고 `검증 시작`을 누릅니다.
5. 미리보기의 오류, 경고, 합계와 기존 버전 차이를 확인합니다.
6. 게시 가능한 버전만 확인 창을 거쳐 게시합니다.

허용 형식은 `.xlsx` 한 개, 최대 20MB입니다. 확장자·크기·ZIP 서명은 비공개 저장소에 기록하기 전에 검사합니다. 파일명은 화면과 감사 메타데이터에만 보존하고 서버 경로에는 생성한 안전한 ID를 사용합니다.

## 3. 오류와 경고

오류는 게시를 차단합니다. 읽을 수 없는 파일, 기준연도 불명, 파일명·헤더 연도 불일치, 37·41열 이외의 구조, 필수 헤더·차원 누락, 빈 데이터, 중복 행 키, 음수·비숫자 학생 수, 재적학생 계산 오류와 정원내·외·성별 소계 오류가 해당합니다.

경고는 관리자가 내용을 확인한 뒤 게시할 수 있습니다. 기존 연도의 새 버전, 행·재적학생·학교 수 급변, 새로운 지역·설립구분·계열·학과상태, 학과군 분류율 하락, 기타·미분류 비중 증가, 비교상 신규·이탈 급증이 해당합니다.

경고 기준은 [`src/config/data-quality-thresholds.json`](../src/config/data-quality-thresholds.json)에 모아 두었습니다.

| 경고 | 초기 기준 | 계산 방법 |
|---|---:|---|
| 행 수 급변 | 20% | `(새 행 수-비교 행 수)/비교 행 수` |
| 재적학생 급변 | 10% | `(새 합계-비교 합계)/비교 합계` |
| 학교 수 급변 | 15% | `(새 학교 수-비교 학교 수)/비교 학교 수` |
| 학과군 분류율 하락 | 5%p | 비교 버전 분류율-새 분류율 |
| 기타·미분류 증가 | 5%p | 새 미분류 비중-비교 버전 비중 |
| 비교상 신규·이탈 급증 | 비교 관측의 50%, 최소 100건 | 신규 관측+이탈 관측 |

## 4. 새 연도·과거 연도·기존 연도 교체

- 새 연도: 검증 후 게시하면 활성 연도에 추가되고 모든 화면과 학과 트렌드가 새 기준연도까지 다시 계산됩니다.
- 누락된 과거 연도: 게시 후 전체 연도 스냅샷을 다시 구성합니다. 추가 연도 이후의 전년 대비와 추세 유형도 새 연도 연결을 사용합니다.
- 기존 연도 교체: 업로드만으로 기존 데이터를 덮어쓰지 않습니다. 새 버전은 `검토 대기`로 남고 관리자가 게시해야 활성 버전이 바뀝니다. 같은 연도에는 활성 버전 하나만 유지됩니다.
- 동일 SHA-256: 중복 업로드를 차단하고 등록된 기존 버전을 화면에 표시합니다.

## 5. 게시와 복구

게시 시 검증된 연도별 정규화 파일을 새 불변 스냅샷으로 먼저 만듭니다. 재적학생 계산을 다시 확인한 후 마지막에 활성 메타데이터 포인터를 새 스냅샷으로 전환합니다. 중간 단계가 실패하면 포인터가 바뀌지 않으므로 일반 대시보드는 기존 데이터를 계속 사용합니다.

복구는 버전 이력의 `복구`를 누르고 확인 창을 승인합니다. 현재 활성 버전은 삭제하지 않고 `이전 버전`으로 남으며, 복구 대상이 활성화되고 새 전체 스냅샷과 감사 기록이 생성됩니다. 물리적 삭제 기능은 없습니다.

## 6. 로컬 저장 위치와 백업

기본 저장 위치는 `data/local-store`이며 전체 폴더가 Git에서 제외됩니다.

- `originals`: 안전한 내부 이름의 원본 XLSX
- `normalized`: 버전별 정규화 JSON
- `reports`: 버전별 검증 보고서
- `snapshots`: 일반 대시보드가 읽는 게시 스냅샷
- `metadata`: 덮어쓰지 않는 버전·게시·복구 감사 메타데이터

백업할 때는 개발 서버를 중지한 뒤 `data/local-store` 전체를 다른 디스크에 복사합니다. 복원할 때도 서버가 중지된 상태에서 전체 폴더 단위로 되돌립니다. 일부 하위 폴더만 복원하면 버전과 원본의 연결이 끊어질 수 있습니다.

## 7. PostgreSQL·Supabase 이전 지점

화면과 업로드 API는 저장 경로를 직접 알지 않습니다. [`DataVersionRepository`](../src/lib/data-store/repository.ts) 구현만 PostgreSQL·Supabase Storage 기반으로 교체할 수 있습니다.

- 버전·감사·활성 포인터: PostgreSQL 테이블과 트랜잭션
- 원본 XLSX·정규화 결과·검증 보고서: 비공개 Supabase Storage 버킷
- 활성 버전 교체: 한 트랜잭션에서 연도별 유일 활성 제약과 감사 행 기록
- 캐시: 게시 스냅샷 ID 또는 데이터 리비전을 캐시 키에 포함

## 8. 인터넷 배포 전 필수 보안 작업

- 관리자 로그인과 역할 기반 권한
- 업로드·게시·복구 API의 서버 측 세션 검증
- 비공개 객체 저장소와 만료형 서명 URL
- 악성 파일 검사, 요청 속도 제한, CSRF 보호와 감사 로그 보존 정책
- 서버 다중 인스턴스를 고려한 DB 트랜잭션·잠금
- 백업 암호화, 복구 훈련, 운영 모니터링과 알림

이번 로컬 단계에는 로그인, Supabase, 클라우드 데이터베이스, 이메일 알림과 실제 배포가 포함되지 않습니다.
